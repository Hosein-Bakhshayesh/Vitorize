## 1. Executive summary

Vitorize is a substantial working store, not a prototype. The repository has clean project boundaries, 48 API controllers, 62 routed Blazor components across storefront/customer/admin areas, a 58-table database, real SQL-backed integration tests, deterministic database deployment, and a broad real-stack Playwright suite. Registration, password/OTP authentication, catalog administration, variants, encrypted gift-code inventory, cart, coupons, checkout, wallet and fake/real Zarinpal adapters, order history, instant/manual/support delivery, tickets, KYC, reviews, content, SEO, logging, outbox processing, and monitoring surfaces all have production code.

The release gate passed on its configured desktop-light project: 394 unit, 111 integration, and 84 Playwright tests. Both independently requested database resets passed, and the release gate performed a third successful reset. A focused security run passed 12/12 across light desktop, dark desktop, and dark mobile.

Launch is nevertheless unsafe. The most serious defect is that products can be priced in Rial or Toman, while cart/order DTOs and persisted orders lose the currency and Zarinpal always receives the raw number as `IRT`. A Rial item can therefore be mislabeled or charged at the wrong magnitude, and mixed-currency carts are arithmetically invalid. A second financial defect allows an administrator to cancel a paid, undelivered order without requiring or recording a refund. The dependency graph also contains a high-severity vulnerable `System.Text.Json 6.0.0`.

Operationally, the checked-in DACPAC remains explicitly a schema candidate pending approval; no executed production backup/restore or clean-server deployment rehearsal was evidenced; real Zarinpal was not exercised; and local Data Protection/media/log storage plus absent forwarded-header configuration make restart and multi-instance behavior deployment-dependent. These are launch conditions, not roadmap polish.

No production code was changed during the audit. Three untracked product images generated by E2E execution were removed after verifying their exact paths. Test baselines were not updated.

### Explicit integrity conclusions

- Duplicate SKU, product/category/brand/tag/blog/page slug, refresh-token hash, payment authority, callback, wallet financial reference, coupon order usage, active gift reservation, and manual delivery are protected by unique indexes.
- Overselling and duplicate gift-code allocation are materially protected by serializable transactions, `sp_getapplock`-style locks, row locks, and the active-reservation unique index. Concurrency integration tests pass.
- Payment callback replay and payment initiation are idempotent and provider verification precedes fulfilment. Payment amount must equal the stored order amount.
- Wallet balance is nonnegative at DB level; debits/credits use a transaction and financial reference idempotency.
- Coupon overuse is protected in the service transaction, but the database does not encode all limits.
- All audited money columns are `(18,2)`, but **currency identity is lost after catalog projection into cart/order**.
- Most timestamps use UTC and DB `sysutcdatetime()` defaults. Persian dates are presentation conversions.
- No optimistic concurrency tokens exist. Financial hot paths compensate with locks; ordinary admin edits remain last-write-wins.
- Soft-delete filtering is service-by-service rather than a global EF query filter, increasing omission risk.
- FK restrictions prevent most orphan database rows. Media files can be orphaned because filesystem lifecycle is not transactional.
- The DACPAC check constraints are not represented in EF fluent configuration, and model index definitions intentionally differ from the deployed schema in documented cases. Runtime SQL is therefore the authoritative contract.

## 6. Storefront audit

### Global and home

Header/navigation, search entry, category navigation, account/cart/wishlist indicators, theme persistence, RTL, responsive layouts, loading/empty/error/404 pages, configurable banners/categories/products/value props/blog/FAQ/footer/social/trust content, broken-image fallback, and SEO metadata exist. Console-quality and visual tests exercise representative pages. Search suggestions are category-oriented rather than a full product suggestion service; there is no true mega-menu model or offline service-worker experience.

### Product listing and search

Server-side category, brand, text, min/max price, discount, availability, sorting, and pagination exist. Active chips, clear-all, mobile filters, and no-results UI exist. Product type, instant-delivery, and discount-tier refinements are applied **after** the server has returned one page, so displayed rows and `TotalCount` can be wrong and matching records on other pages are undiscoverable. Rating filtering is absent; delivery filtering is not a complete Instant/Manual/Support selector. Filter/page state is not round-tripped to the query string. Primary server sorting uses stable secondary date/order keys, but client-only filtering breaks page stability.

### Product details

The page has gallery, variants, live price, stock, product/delivery labels, sanitized CKEditor HTML and inline public images, features, dynamic fields, review summary/list, related products, wishlist, share/copy, responsive layout, canonical/Open Graph/Twitter and Product/Breadcrumb structured data. Structured product currency converts Toman to IRR correctly, which contrasts with checkout. There is no zoom. Generic “instant/code in seconds” trust text can appear on manual/support products, and explicit SupportRequired/refund/return/terms disclosures are incomplete.

### Cart and checkout

The cart persists for authenticated users, distinguishes variant/input fingerprints, merges exact duplicates, updates/removes, previews coupons, and is repriced at checkout. Checkout revalidates active products/variants, quantity, KYC, stock, coupons, and final amount inside a serializable transaction. It has per-click idempotency, wallet and gateway flows, callback replay handling, cancellation/failure paths, compensation on post-verification fulfilment failure, and order confirmation.

There is no guest cart, mixed wallet/gateway payment, terms acknowledgement, or resumable “pending payment” checkout recovery. Free products are accepted by admin validation and explicitly tested as a supported persisted state, but both wallet and gateway payment reject `FinalAmount <= 0`. The payment-result page trusts `?Paid=1` for display/cart clearing; this cannot mark an API payment paid but can mislead the customer and clear local cart state.

### Customer account

Profile, password change, order list/details, code library/copy, tickets/replies, notifications, wallet/transactions/top-up, wishlist, reviews, KYC/document upload, and logout are implemented. Mobile OTP login/recovery exists. Missing or incomplete: address management, email verification, 2FA (the enum exists but the service rejects the purpose), access-token refresh in the Web API client, server refresh-token revocation on Web logout, session/device list/revocation, and account deletion/data-request workflow.

Admin type and delivery choices are independent, so all 15 enum combinations can be persisted and traverse the generic storefront/cart/checkout path. Delivery behavior is determined by delivery mode, not product type.

|---|---|---|---|
| GiftCard | Functional; E2E with base and variants | Functional; E2E | Functional by generic path; partial automated coverage |
| GameAccount | Functional if codes stocked; partial coverage | Functional; E2E | Functional by generic path; GTA VI E2E covers opt-in support |
| GameService | Functional if codes stocked; partial coverage | Functional; partial coverage | Functional; E2E |
| Subscription | Functional; E2E | Functional; partial coverage | Functional by generic path; partial coverage |

**Instant:** code selection/reservation/expiration/concurrent purchase/no-duplicate-sale/owner visibility/masking/failure release are implemented and SQL-tested. Codes are allocated only after payment verification. Refunding a delivered code cannot revoke a secret already seen; this is an unavoidable policy concern that should require operator acknowledgement.

**Manual:** paid items appear in the order workflow; admin delivery is encrypted, hashed, unique per item, customer-notified, audited, and retry-safe. There is no assignment/ownership queue. Admin can separately mark the whole order complete before every item is delivered.

**SupportRequired:** customer-created and opt-in automatic ticket flows both work; owner isolation, visible replies, internal notes, close/reopen, notification privacy, and retry idempotency are covered. The automatic subject is hard-coded to “GTA VI” for every product. The application enforces one ticket per order only by query/lock, not a unique DB constraint; an existing customer ticket can suppress auto-creation, and only the first qualifying item gets `SupportTicketId`.

## 9. Payment and financial audit

### Present and verified

- Zarinpal request/verify adapter with provider authority/reference handling.
- Wallet top-up, wallet checkout, serialized debit/credit, nonnegative DB balance.
- Payment and callback idempotency indexes plus per-order/payment application locks.
- Stored-order amount equality checks before verification/fulfilment.
- Coupon recalculation and transactional usage accounting.
- Full refund service: immediate wallet refund or two-step manual gateway refund.
- Automatic wallet compensation if provider verification succeeds but fulfilment fails.
- Pending-Zarinpal reconciliation in API/admin service and maintenance worker.
- Financial audit logs, order status histories, notifications, and outbox SMS.

### Missing or unsafe

- **Currency:** catalog `CurrencyType` never enters cart/order/payment DTOs or order rows. Zarinpal submits raw `FinalAmount` with `currency = "IRT"`. Mixed currencies are not rejected or converted.
- **Paid cancellation:** `CancelOrderAsync` blocks completed/delivered/cancelled orders but does not block `PaymentStatus.Paid`, initiate a refund, or change payment state.
- **Premature completion:** `CompleteOrderAsync` checks only paid/not-cancelled and can complete an undelivered manual/support order.
- `ZarinpalSandbox` is seeded/documented but never read; endpoint URL settings control behavior. Health reads `ZarinpalIsSandbox`, a different nonexistent key.
- Missing merchant ID degrades safely in Production, but live URL/merchant/callback/origin consistency is not startup-validated.
- Real provider calls, cancellation returns, settlement, under/overpayment at provider, and production callback routing were not externally exercised.
- No partial refund, chargeback/dispute, settlement ledger, payout reconciliation, tax model, or refund UI.
- Free/zero-total checkout cannot complete despite admin support for zero price.
- Monetary rounding is decimal-based but no explicit currency rounding policy is centralized.

## 12. Performance audit

- Response compression and one-week immutable static caching are enabled; public pages prerender; home data calls are parallel.
- Product projections use correlated counts for gift-code stock/reviews. EF emits SQL subqueries rather than application N+1 calls, but realistic-size query plans were not captured.
- Admin payment and several other lists request up to 500 rows and then filter/page in the Blazor circuit. Counts and memory/network cost become incorrect at larger data volumes.
- Listing-only product/delivery/tier filters operate client-side on a server page, causing extra requests and incorrect pagination.
- Blazor Server creates stateful circuits with a 256 KB hub message limit; scale-out/cache/backplane behavior is undefined.
- CKEditor and the large Lucide sprite are loaded on relevant admin pages; no leak was observed, but there is no long-running circuit/heap test.
- The Playwright performance test checks bounded document size/layout for one product, not API latency, SQL query count, p95, throughput, or memory.
- `k6` was not installed, so checked-in load profiles were inventoried but not executed.
- Local full visual pages are large (home baselines reach thousands of pixels), suggesting a high DOM/content cost that should be measured on mobile hardware.

## 27. Final conclusion

Vitorize has enough implemented product to become a commercial store, and its strongest qualities are transactional gift-code fulfilment, authorization boundaries, sensitive-data handling, database deployment verification, and unusually broad real-stack QA. Green tests do not negate the audited launch blockers: currency is not preserved, paid cancellation is financially unsafe, a high-severity vulnerable package is present, and the current production database/payment/backup/host contracts are not release-proven.

The correct next step is a focused launch-hardening release in the order in section 23, followed by an approved database deployment, backup/restore drill, live-provider certification, restart/multi-instance rehearsal, clean advisory scan, and a deterministic all-project release gate. The broader roadmap should not begin until those conditions are met.
