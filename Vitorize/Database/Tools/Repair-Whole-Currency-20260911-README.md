# اصلاح قیمت‌های اعشاری ـ ۲۰۲۶/۰۹/۱۱

فایل همراه: `Repair-Whole-Currency-20260911.sql`

## قاعده

واحد پول عوض نمی‌شود: تومان، تومان می‌ماند و ریال، ریال. تبدیل ضربدر ۱۰ انجام نمی‌شود.
قیمت واحد به نزدیک‌ترین عدد صحیح گرد می‌شود؛ نیم به بالا. سپس تعداد ضرب می‌شود؛ تخفیف مبلغی و مالیات هم عدد صحیح می‌شوند. نرخ درصدی مالیات/تخفیف می‌تواند اعشاری باقی بماند.

مثال: قیمت واحد ۱۹۸٬۷۸۲٫۱۰ به ۱۹۸٬۷۸۲، مالیات ۱٪ به ۱٬۹۸۸ و مبلغ نهایی به ۲۰۰٬۷۷۰ تومان تبدیل می‌شود. دو عدد از همین کالا: ۳۹۷٬۵۶۴ + ۳٬۹۷۶ = ۴۰۱٬۵۴۰ تومان.

## اجرا

1. فایل SQL را در SSMS باز کنید و دیتابیس `VitorizeDb` را انتخاب کنید. کل فایل را اجرا کنید؛ مقدار پیش‌فرض `@Apply = 0` فقط پیش‌نمایش است و اطلاعات اصلی را تغییر نمی‌دهد.
2. خروجی‌های قیمت محصول، واریانت و سفارش را بررسی کنید. ستون `SkipReason` خالی یعنی سفارش قابل اصلاح است. خروجی را برای بررسی نگه دارید.
3. قبل از اعمال، از دیتابیس بکاپ کامل قابل بازیابی بگیرید. Web و API و پردازش‌های پس‌زمینه را متوقف کنید؛ صرفاً مخفی‌کردن دکمه خرید یا maintenance ظاهری کافی نیست.
4. کد جدید را در همین بازه نگهداری مستقر کنید. فایل SQL را با `@Apply = 1` و `@MaintenanceConfirmed = 1` دوباره به‌طور کامل اجرا کنید. اگر خطا داد، سرویس را باز نکنید تا علت مشخص شود.
5. مقدار `RepairAuditId` و نتیجه نهایی را نگه دارید. قبل/بعد مقادیر اصلاح‌شده در `AuditLogs` ثبت می‌شود؛ این جای بکاپ کامل را نمی‌گیرد.
6. Web و API را با نسخه جدید راه‌اندازی کنید. مبلغ سبد، سفارش و صفحه درگاه را تطبیق دهید. بررسی واقعی درگاه باید با اجازه و در محیط عملیاتی انجام شود؛ تست‌های خودکار این تغییر پرداخت واقعی انجام نمی‌دهند.

## چه چیزهایی تغییر می‌کند؟

- قیمت و تخفیف مبلغی محصولات حذف‌نشده و واریانت‌های آن‌ها، و قیمت واحد سبدها که واقعاً اعشار دارند.
- سفارش‌های در انتظار پرداخت با مبلغ اعشاری و فاقد شواهد پرداخت/تحویل، بر اساس قیمت اقلام و نرخ مالیات ذخیره‌شده همان سفارش، نه قیمت جدید روز محصول.
- تلاش محلی READY بدون درخواست بانکی به «ناموفق/نیازمند تلاش جدید» تبدیل می‌شود. دکمه پرداخت، تلاش تازه با مبلغ اصلاح‌شده می‌سازد.

## چه چیزهایی دست‌نخورده می‌ماند؟

- سفارش‌های پرداخت‌شده، تکمیل‌شده، لغوشده و برگشت‌وجه‌شده.
- مبلغ و سوابق تلاش‌های پرداخت قبلی؛ حتی تلاش‌های ناموفق. این‌ها برای حسابرسی حفظ می‌شوند و با سفارش اصلاح‌شده الزاماً مبلغ یکسان ندارند.
- سفارش دارای Authority، callback، شماره پیگیری، پرداخت INITIALIZING، فعالیت کیف پول/مصرف کوپن، تحویل یا وضعیت عملیاتی احراز هویت: با علت در `SkipReason` کنار گذاشته می‌شود. حذف شرط‌ها برای اجبار اصلاح مجاز نیست؛ ابتدا تطبیق وضعیت بانکی لازم است.
- سفارش‌هایی که گردکردن مبلغ آن‌ها مرز احراز هویت را رد می‌کند؛ نیازمند بررسی دستی‌اند.

این اسکریپت بانک را استعلام نمی‌کند، رزرو موجودی را آزاد نمی‌کند و احراز هویت را تأیید نمی‌کند. فایل SQL به‌تنهایی جلوی تولید مجدد اعشار توسط نسخه قدیمی کد را نمی‌گیرد؛ کد جدید هم باید مستقر شود.
